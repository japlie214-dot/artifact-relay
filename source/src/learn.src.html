    Lesson 0

    What you will be able to do

    By the end, you will have a Claude app that Claude can operate, read and screenshot while you watch: type in its boxes, click its buttons, read what it shows, and report back.

    That includes apps that call tools like Snowflake. Claude does not need a separate login or a server. Everything goes through a small shared database that every Claude app can have, and each person gets a private channel in it.

    What you need

    • A Claude app where you can publish artifacts (a Claude app is a web page that opens inside Claude).
    • A text editor and a basic idea of HTML. You do not need to be a programmer; every line of code is explained.
    • About an hour for the lessons, plus time to try it on your own app.

    Who does what

    YouClaude
    Write or edit the page (this guide gives you the code)
    Keep Claude's app open when you want it driven
    Click Allow when a connector asks
    Decide who the app is shared with    		 Publishes the page with the right settings
    Opens the app if it is closed
    Writes commands into your private channel
    Reads results and screenshots and tells you what happened
    Be clear about one thing. Understanding and building the page is something you can do alone with this guide. Publishing the page and writing into its database are done through Claude's own tools, so you ask Claude for those two jobs. The Publish and run lesson has the exact sentences to use.

    How this guide teaches

    The Playground lesson runs the real bridge code against a practice app. Build it from zero builds the bridge in small stages. The Starter kit lesson gives you files to copy so you never start from a blank page. Pitfalls and best practices lists what we found and how each is handled, and best-practices.html is a one-page list of dos, don'ts and a checklist. The Stress-test lab runs the full test suite in your browser and lets you break the bridge on purpose to watch the tests catch it.

    Lesson 1

    How Claude can reach inside an app

    Claude does not click anything. It leaves a note in your private area of the app's database, and the app reads the note and does the work itself.

    Three ideas that make this work

    The app is a real session

    Your app runs inside your open Claude window, signed in as you. If it calls Snowflake, it uses your Snowflake connection. Nothing is borrowed.

    The app is never reloaded

    The app listens to its database. A new note arrives and a function runs. The page stays as it is, so text you typed and results on screen are kept.

    Commands are data, not code

    A command is a list of small steps like fill and click. The app has a fixed list of steps it understands, so a command can only do what you built in.

    Lesson 2

    Three parts and a few words

    Once you know these three parts, the rest of the guide is detail.

    Part 1

    The app's database

    Every Claude app can have a small shared database. It holds documents (little bundles of data) grouped into collections (like folders). Each person gets a private area, data/users/<their id>/, that nobody else can read, not even the app's owner. We use four collections inside it.

    cmd commands Claude writes
    res results the app writes
    snap screenshots the app writes
    meta a hello note when the page opens

    Part 2

    The bridge in your page

    A block of JavaScript in your page. It listens to cmd, runs each step on the page, then writes to res and snap. You will build it in the Build it from zero lesson.

    Part 3

    Claude's database tool

    A tool called ArtifactData lets Claude read and write that database from chat. In a path, the word me means "the person Claude is working for", so Claude only ever writes to your own channel.

    What the documents look like

    Counting path pieces (a very common mistake)

    Documents have an even number of pieces in their path, collections an odd number. data/users/u1/rc has 4 pieces, so it is a document. Add /cmd and you have 5, a collection. Add an id and you have 6, a document again. The practice database in this guide enforces the same rule.

    Words you will see

    WordPlain meaning
    Artifact / Claude appA web page published from Claude that opens inside Claude.
    CapabilityA permission the page asks for, such as db (database) or mcp (call connectors like Snowflake).
    ConnectorA link between Claude and another service, such as Snowflake.
    SelectorA short text that points at one thing on the page, like #add for the element whose id is add.
    SubscriptionA standing request: "tell me whenever this data changes".
    LeaseA short claim on a document so that only one tab works on it at a time.

    Things to try

    • Draft, not submitted: type nothing yourself. Send the example. The bridge fills the Task and Note fields, and read shows the typed text even though nothing was submitted.
    • Slow work: the command waits until "Synced" appears. Then try deleting the wait_for step and see what happens.

    If the page is closed or not showing
    
  
    The routine Claude follows, and that you can ask for in plain words:
    
  
      
    
    • Write the command. It waits in cmd as "pending" and runs, oldest first, when a page opens.
      • 
    
    • Look for the answer after about 10 seconds. If there is none, the page is probably not open.
      • 
    
    • Claude shows the artifact pane and opens the app, waits up to about 30 seconds, and tries once more.
      • 
    
    • Still silent? Claude tells you, and you open the app yourself. That is the reliable fallback.
      • 
    
    • Add expires to anything that must not run late.
      • 
  
    
  
    What was seen in a real test. With the tab closed, a command stayed pending. Claude's first open request did nothing for about 100 seconds. After showing the artifact pane and sending open a second time, the page loaded within about 25 seconds, said hello, and ran the waiting command. It was a fresh page, so anything typed into the old one was gone. So reopening works, but it is slow, it was not reliable on the first try, and it needs the Claude app to be running and in view.
    

  
    If your app also calls a connector
    
  
    Add the mcp capability with the connector's exact display name and the tools you call. The first time the app calls it, Claude asks you to allow it. That click is yours alone, and the page waits for it.
    
  
    

    



    
  
    Lesson 6
    
  
    Ready-made commands
    
  
    Copy these, change the selectors to match your app, and send them through Claude. The ones marked "Try" run in the playground.
    
  
    
  
    Every step you can use
    
  
    
    
    StepFieldsWhat it does
    
    
    pingnoneAnswers right away. Shows the bridge version and whether the page is visible.
    
    
    readselector?Everything on screen: text, lists, tables, and every control with its current value (including text typed but not submitted).
    
    
    inspectselector?Only the controls: selector, label, value, disabled, visible.
    
    
    fillselector, value, index?Types into a text field or text area, then reads the value back.
    
    
    selectselector, value or labelChooses an option in a dropdown.
    
    
    checkselector, checked?Ticks or unticks a checkbox.
    
    
    clickselector, index?, force?Clicks a button or link. Refuses disabled or hidden elements.
    
    
    presskey, selector?Sends a key to the page's handlers. It does not submit forms.
    
    
    waitmsPauses (up to 10 seconds).
    
    
    wait_forselector, textIncludes?, gone?, timeoutMs?Waits until something appears (or disappears). Fails the command if it never does.
    
    
    textselector, index?The visible text of one element. On a field, its value.
    
    
    callname, args?Runs a named function you registered in the page.
    
    
    screenshotselector?Saves a picture of the page (or one area) for Claude to look at.
    
  
    
  
    Any step can add "optional": true so that if it fails the command carries on. The failure is still recorded.

    Lesson 8
    
  
    Prove it works, then try to break it
    
  
    These tests run in your browser right now against the same bridge code. Most of them are negative tests: they send bad commands, close pages mid-command, open two tabs, and make the database fail.
    

  
    
  
    

  
    Break the bridge on purpose
    
  
    A test that never fails proves nothing. This is called mutation testing: we damage the bridge in one specific way and check that a test notices. Pick a damage, run it, and the bridge is restored afterwards.
    
  
    
  
    

  
    How a test is written
    
  
    
  
    Add your own by copying one in source/tests.js, then run node source/build.mjs to rebuild this guide and tests/stress-tests.html.
    
  
    What these tests cannot prove. They use a stand-in database, so some real-world things need a real check: how the real database delivers changes, and what a real Claude window does when it is hidden or closed. The template was also tested on the real database; the pitfalls lesson says what was seen there.
    

    



    
  
    Lesson 9
    
  
    Two people, two Snowflake logins, one app
    
  
    Everyone can use the same app at the same time with their own login, and each person's remote control stays private to them.
    

  
    
    
    Person APerson B
    
    
    Runs the app intheir own Claude windowtheir own Claude window
    
    
    Snowflake connectiontheir own logintheir own login
    
    
    Remote-control channeldata/users/A/rcdata/users/B/rc
    
    
    Who can read the resultsonly Aonly B (not even the app's owner)
    
    
    Who can drive the pageA's own Claude sessionB's own Claude session
    
  
    

  
    What this means
    
  
      
    
    • Queries run under each person's own Snowflake login, at the same time, without interfering. The page calls the connector as whoever is looking at it.
      • 
    
    • When Claude writes to me, it writes to that person's channel. It cannot drive anybody else's page.
      • 
    
    • Results and screenshots are private by default, which fixes the biggest weakness of a shared command area.
      • 
    
    • The app's owner cannot read other people's channels, and cannot remote-control their pages either.
      • 
  
    

  
    What each person needs
    
  
      
    
    • Access to the app at Contributor level or higher. Viewers can use the app, but the panel will say off because they cannot write to their own channel.
      • 
    
    • Their own Snowflake connector, and their own Allow click the first time.
      • 
    
    • Their own Claude session to give the commands.
      • 
  
    
  
    Housekeeping. An app's database holds at most 25,000 documents in total, shared by everyone. Each command leaves a command document and a result document, and screenshots add more. Ask Claude to delete old ones now and then, or add a cleanup step to your routine.
    
  
    Not tested here. I tested one person on the real database. The rules above come from how the database's private areas work and from the tests with a stand-in database. Try it with a second person before relying on it.
    

    



    
  
    Lesson 10
    
  
    What this can and cannot do
    
  
    You are letting something else press buttons in a signed-in session, so the guard rails matter.
    
  
    
    
    Private by design
    Commands and results live under your own id. Other people cannot read them and cannot write to them. Claude writes to me, so it only reaches the person it is working for.
    
    
    A fixed list of steps
    Nothing is run as code. Unknown steps make the whole command invalid, and a command is limited to 40 steps.
    
    
    It acts as you
    If the app runs a Snowflake query, it runs under your Snowflake login. Treat every command like your own click.
    
    
    You stay in control
    The panel shows what ran. Pause holds commands. Closing the page stops everything. Commands never run twice and are never retried after an interruption.
    
    
    Old commands
    A waiting command runs when the page opens. Add expires to anything that must not run late.
    
    
    Be careful what you capture
    Screenshots and read results hold whatever is on screen. They sit in your private area, but anything you share the app's data with could see shared documents, so keep secrets out of shared paths.
    
  
    
  
    Honest limits
    
  
      
    
    • The app must be open in Claude. If it is closed, commands wait.
      • 
    
    • Screenshots are redrawn from the page, not photographed, so unusual styles can look different. In a real test, a two-line note appeared on one line in the picture, while read returned it exactly. Use read for exact values.
      • 
    
    • Clicks are synthetic. Hover effects, dragging and drawing with the mouse are not covered. Use a call step or write data directly instead.
      • 
    
    • A document holds at most 256 KB and an app at most 25,000 documents.
      • 
    
    • Keep the app visible while commands run, because browsers slow hidden tabs. ping reports visibility.
      •
